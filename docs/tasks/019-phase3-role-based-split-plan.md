# Phase 3 三角色清單整合：切割與實作策略

**日期**: 2026-09-17
**分析人員**: Claude Sonnet 5
**狀態**: 規劃文件，未實作
**輸入文件**: `016-feature-gap-analysis.md`（賣家）、`017-buyer-feature-list.md`（買家）、
`018-maintainer-feature-list.md`（維護者）

---

## 目的

016/017/018 分別從賣家、買家、維護者三個角度各自列出功能缺口，這是刻意的——同一個系統，
不同角色關心的東西真的不一樣。但三份清單有大量底層重疊（同一張表、同一組 API），如果照三份
清單各自的「建議執行路徑」分開排程，會出現：

1. **同一張表被改三次**：例如 `shop_order` 在 017 要加 `order_status`/收件欄位，
   018 建議先做 RBAC 才動 member 相關表——如果不協調順序，可能改完 A 又要為了 B 再 migration 一次。
2. **同一組端點被規劃兩次**：017 的「訂單歷史查詢」跟 016 的「訂單查詢」本質是同一個
   `GET /api/orders`，差別只在查詢範圍（本人 vs 全店）。
3. **依賴關係被忽略**：018 的 RBAC（角色權限）是 016 商品管理後台「區分賣家 vs 一般用戶角色」
   的地基，也是 017 個人資料存取控制的地基——如果 RBAC 沒有先做，其他兩份清單裡標了
   「需要角色區分」的項目全部卡住或要重做。

本文不重複列出功能本身（那是 016/017/018 的工作），只處理**三份清單合起來要怎麼切、
先後順序怎麼排、每個切下來的任務要怎麼寫提示詞、丟給誰做**。

## 一、重疊盤點表

| 底層變更 | 016（賣家） | 017（買家） | 018（維護者） | 建議做法 |
|---|---|---|---|---|
| `member` 表加 `role` 欄位 | 2.1「區分賣家 vs 一般用戶角色」依賴此項 | 間接依賴（帳號類型判斷） | 1.1 RBAC，本項的擁有者 | **由 018 的 RBAC 任務一次做完**，016/017 直接引用結果，不重複 migration |
| `shop_order` 加 `order_status` | 2.2 訂單狀態流程（營運端寫入） | 1.3 訂單狀態追蹤（買家端讀取） | 無直接需求，但索引/效能監控會涉及 | **由 017 的 Phase 3.0 任務做 schema**，016 的狀態轉移邏輯在 schema 之後接著做 |
| `shop_order`/新表 加收件地址 | 間接相關（出貨需要地址） | 1.2 收件資訊、2.2 地址簿 | 無 | **由 017 做**，016 出貨相關功能直接讀取 |
| `GET /api/orders` 查詢端點 | 1.1 訂單查詢（範圍：全店/賣家後台） | 1.1 訂單歷史（範圍：僅本人） | 2.4 需要 member_id 索引支撐 | **同一組 API，用角色/範圍參數區分**，不要做成兩套查詢邏輯；索引由 018 提醒但實作跟著這個任務一起做 |
| 商品管理 CRUD（編輯/下架） | 2.1 商品管理介面 | 無 | 3.4 軟刪除（status 欄位是這項的前提） | **018 的軟刪除 schema 先行**，016 的管理介面 UI/端點在其上實作 |
| 評論系統 | 3.1（後台管理/審核視角） | 2.4（買家寫評論/看評論視角） | 無 | **017 做核心 CRUD + 防灌水邏輯**，016 之後補管理/隱藏端點，避免兩邊各自定義 `product_reviews` schema |
| 優惠券 | 3.2（賣家/營運設定與驗證邏輯） | 3.2（買家輸入框，前端） | 無 | **016 做後端**，017 做前端輸入，明確的前後端分工，不是重疊而是介面契約，需先對齊 API 形狀 |
| 密鑰/環境設定 | 無 | 無 | 2.3 密鑰管理審查 | 純 018 範圍，跟 016/017 無關 |

**結論**：RBAC（018 1.1）、`order_status`/收件地址 schema（017 1.2/1.3）、商品軟刪除 schema（018 3.4）
是三份清單中最多下游依賴的「基礎設施」項目，應該排在最前面，而且要一次做完、不要被拆散到
不同時間點各自加欄位。

## 二、實作順序（跨三份清單整合後的 Phase 3 時間軸）

### Phase 3.0 — 基礎設施（阻塞其他所有項目，優先度最高）

依「誰阻塞誰最多」排序，同一階段內若無互相依賴可並行（不同分支、不同 checkout）：

1. **RBAC 角色權限**（018 §1.1）——member 加 role、JWT claim、路由角色檢查
   - 風險分級：**Critical**（authorization 變更，依 AGENTS.md 需要獨立審查）
2. **訂單歷史查詢 + 訂單狀態 + 收件資訊 schema**（017 §1.1/1.2/1.3，三者共用同一次 `shop_order`
   migration，合併成一個任務比分三次改動安全）
   - 風險分級：**Medium**（新增欄位為非破壞性 migration，但涉及 order 核心表，建議至少跑一次完整
     回歸測試）
3. **系統監控 / 健康檢查**（018 §1.2）——與上述兩項無資料相依，**可並行**
   - 風險分級：**Small-Medium**
4. **資料備份與還原演練**（018 §1.3）——純維運腳本，**可並行**
   - 風險分級：**Small**

> RBAC 與「訂單歷史 schema」兩者理論上互相獨立（一個動 member，一個動 shop_order），
> 可以兩個分支並行；但依 AGENTS.md「Parallel worker policy」，兩個同屬 Heavy 分類的任務
> 不建議同時起兩個重量級 session，避免互相干擾同一份 checkout 的 review 資源。建議：
> RBAC 先進 review 佇列（Critical，需要獨立審查，排隊時間較長），訂單 schema 的實作可以
> 利用這段等待時間並行推進。

### Phase 3.1 — 角色相關功能（依賴 Phase 3.0 的 RBAC）

- 忘記/修改密碼（017 §1.4）
- 個人資料管理 + 地址簿 + 購物車持久化（017 §2.1/2.2/2.3）
- 商品評論核心功能（017 §2.4，後端 CRUD + 防灌水）
- 商品管理後台（016 §2.1，依賴 RBAC 的角色檢查 + 018 的軟刪除 schema）
- 訂單狀態流程的營運端邏輯（016 §2.2，依賴 017 已建的 `order_status` 欄位）
- 操作稽核日誌、錯誤追蹤/告警、密鑰管理盤點、API 文件、商品軟刪除（018 §2.1/2.2/2.3/3.2/3.4）

### Phase 3.2 — 轉化與長期維運

- 金流整合（016 §1.2）
- 收藏/心願單（016 §2.3 = 017 §3.1，同一項目）
- 優惠券（016 §3.2 後端 + 017 §3.2 前端，需先對齊 API 契約）
- 評論管理後台（016 §3.1 的後台部分）
- CI/CD 部署自動化、效能基線長期追蹤（018 §3.1/3.3）

### Phase 3.3+ — 可選

- 到貨/降價通知（017 §3.3）
- 退換貨自助申請（017 §3.4，依賴訂單狀態機已存在）
- 推薦系統（016 §3.3）

## 三、風險分級與協作模式（套用 AGENTS.md）

| 任務 | AGENTS.md 分級 | 協作模式 |
|---|---|---|
| RBAC 角色權限 | Critical（authorization） | 一方實作，另一方（Codex/Claude 互換）獨立審查；審查者從需求推導預期行為，看 code/test 再看實作說明 |
| 訂單 schema（status/收件地址） | Medium（order 核心表的 schema 變更） | 一方實作 + 目標測試；範圍夠小可不強制第二人審查，但建議跑一次完整回歸 |
| 系統監控、備份演練、API 文件 | Small | 單一 agent + 對應驗證即可，不需強制委派或第二審查者 |
| 商品評論、優惠券、推薦系統 | Medium | 視實際牽動的 concurrency/transaction 範圍決定，若只涉及新表+CRUD 屬 Medium；若牽動 order 金額計算則提升為 Critical |
| 金流整合 | Critical（payment） | 必須獨立審查；且需要真實/測試支付商帳號才能做端對端驗收，不能只靠靜態審查 |

## 四、分支策略

依既有的 `phase2-branching-strategy` 慣例（`advanced-v2` 保留給已整合/已審查的成果，每個
Phase 候選項目開獨立分支）：

```
advanced-v2
 ├── phase3-rbac-role-permission          (018 §1.1，Critical，獨立審查)
 ├── phase3-order-schema-status-address   (017 §1.1/1.2/1.3 合併 migration)
 ├── phase3-observability-actuator        (018 §1.2)
 ├── phase3-backup-restore-drill          (018 §1.3)
 ├── phase3-buyer-account-management      (017 §1.4/2.1/2.2/2.3，依賴 rbac 分支已合併)
 ├── phase3-product-reviews               (017 §2.4，之後 016 §3.1 在此分支基礎上加後台)
 ├── phase3-seller-admin-panel            (016 §2.1，依賴 rbac + product soft-delete 已合併)
 └── ...
```

**一個 checkout 一個 writer**：RBAC、訂單 schema 這兩個 Phase 3.0 任務如果要並行，
必須用不同 worktree（`git worktree add`），不要在同一個工作目錄切分支來回切換，避免
未 commit 的變更互相污染（本專案已在 `.claude/worktrees/` 下有先例）。

## 五、提示詞切割範本（套用 prompt-scope-control 規則）

三份清單各自的「提示詞範本」章節已經示範了單一任務的 A/B/C 拆法（016/017/018 文件內的
「Phase 3.0 提示詞」段落）。這裡示範**跨清單依賴**的任務——RBAC——完整的三階段拆法，
因為它是本次整合中唯一同時被三份清單引用、且屬於 Critical 分級的項目：

```markdown
### A（定位）— 獨立提示詞/session，只讀不改
背景：esun-shopping 需要角色權限，才能讓 016/017/018 中標注「需要角色區分」的功能有地方掛。
任務：盤點目前所有寫入端點（POST/PUT/DELETE）、目前的保護狀態（公開/需登入/需特定角色），
列出這次 RBAC 上線後每個端點該對應到哪個最低角色，寫成一份端點-角色對照表。
範圍：只讀 controller/security 相關檔案，不修改任何程式碼，不跑測試。
產出：docs/tasks/0xx-rbac-endpoint-audit.md（對照表 + 建議角色）

### B（實作）— 獨立提示詞/session，只做 A 階段列出的範圍
背景：docs/tasks/0xx-rbac-endpoint-audit.md 已列出端點-角色對照表。
任務：只依照該對照表新增 member.role 欄位、JWT role claim、路由角色檢查；不擴大範圍去改
A 階段沒提到的端點，不做前端 UI 調整（那是後續任務）。
範圍：可讀/改 member 相關 DTO/Entity、AuthService、JwtService、JwtAuthFilter、
04_member.sql、A 階段對照表列出的 controller。
驗證：mvn clean test（全量，確認無回歸）+ 針對新角色檢查的目標測試。

### C（驗收）— 另開獨立提示詞/session，只看 diff 與回歸結果
背景：B 階段已完成 RBAC 實作並自行跑過測試。
任務：只看這次的 diff 與測試結果，比對是否符合 A 階段的對照表、是否有端點被遺漏或
誤擋；不重新完整審查一次程式碼風格，不擴大成全庫掃描。
產出：PASS / FAIL / BLOCKED，若 FAIL 用 AGENTS.md 的 CODEX → CLAUDE CORRECTION TASK 格式回報。
```

同樣的 A/B/C 拆法適用於「訂單 schema 合併 migration」（017 §1.1-1.3）與「金流整合」
（016 §1.2，Critical 等級），只是 A 階段的產出不同（前者是「這次 migration 要動哪些欄位、
影響哪些既有查詢」，後者是「選定支付商 + API 串接範圍盤點」）。

**每個切下來的提示詞都要明確寫「可以讀哪些檔案／可以改哪些檔案／要跑哪些測試」**——這是
`prompt-scope-control` 記憶裡使用者明確糾正過的規則：不能只在文件開頭放一段抽象宣告，
實際會被複製去下指令的清單本身也要套用 A/B/C 拆分，本文件第二節「實作順序」列出的每一項
在真正展開成提示詞時都要照這個範本拆，不能整項直接複製給 agent。

## 六、給下一步的具體建議

1. **不要同時展開 016/017/018 三份清單的 Phase 3.0**。先做本文件第二節排定的四項基礎設施
   （RBAC、訂單 schema、監控、備份），這四項完成並合併回 `advanced-v2` 之後，三份清單裡
   後續依賴角色/訂單狀態/收件地址的項目才有穩定的地基可以疊上去。
2. **RBAC 是第一個要展開成 A/B/C 三階段提示詞的任務**，因為它的下游依賴最多、風險分級最高
   （Critical，需要獨立審查）。
3. 展開任何一項到實際提示詞之前，先確認 `advanced-v2` 是否已被其他 session 推進（依
   `phase2-branching-strategy` 慣例檢查是否需要先 reconcile），避免在過時的基礎上開分支。
4. 每完成一個 Phase 3.0 項目，回來更新本文件第二節的時間軸勾稽狀態，而不是散落在三份
   清單各自的「建議執行路徑」段落裡各自標記——避免進度紀錄跟功能盤點混在一起難以追蹤。
